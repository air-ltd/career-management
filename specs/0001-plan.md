# Plan: career-management-document

**Status:** `Draft`
**Depends on:** nothing yet — this is the first spec for this repository
**Reference implementation:** `air-ltd/personal-time-tracker` (stack, spec conventions, Dropbox sync)
**Legacy application:** `jaredchurch/cv` (Flask + SQLite, source at `tmp/cv`)

Rewrite the legacy Flask career-management app as a static GitHub Pages site, with
Dropbox as the sync backend and the browser as the only runtime.

This document is the plan and the specification combined. Once it is accepted it
should be split into numbered specs under `SPECS/`, following the layout in
`personal-time-tracker`. Until then it is one file so that decisions can be argued
with in one place.

Requirement keywords follow [RFC 2119](https://www.ietf.org/rfc/rfc2119):
`MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY`.

---

## 1. Problem

The legacy app (`jaredchurch/cv`, v2.0.5) is a single-user Flask application
served from a workstation. It works, but it constrains the user in ways that are
no longer acceptable:

- **It needs a machine that is on.** `app.py` binds `0.0.0.0:8000` with the
  Werkzeug debugger enabled and no authentication of any kind. The README's
  documented run path is `cd www && python3 db_upgrade.py && python3 app.py`.
- **The data is in one SQLite file on one disk.** `script/env.ps1` shows the
  production location was a Samba share, refreshed into the dev directory by hand.
  There is no second copy that is not a file copy.
- **It is not portable.** `db.py` opens `./data/career_management.sqlite3` relative
  to the process CWD, and `upgrade()` reads `./sql/`. Running it from anywhere but
  `www/` fails. The author flagged this himself: *"I don't know why I don't just
  have the db_upgrade as the first step in app.py."*
- **The editing UI has degraded.** It was server-rendered with Jinja, every edit
  form in the document is present in the DOM at page load, and stories are
  rendered through `{{ value.story.replace('\n', '<br>') | safe }}` — an escaping
  bypass that is the documented cause of the data corruption repaired by schema
  migration v4 (`04_upgrade_from_3.sql` strips `&amp;`, `&#039;`, `&quot;`,
  `&#37;` out of eleven text columns).
- **It has known runtime bugs** that have never been fixed. See §9.

None of these are worth fixing in place. The Flask/Jinja/SQLite shape is the
cause, not the symptom, and the target — a static site — cannot host a Flask app
at all.

## 2. Goals

| # | Goal |
| --- | --- |
| G1 | Runs as a static GitHub Pages site. No server, no database, no build step the user has to run. |
| G2 | Works offline. The network is an optimisation, never a prerequisite. |
| G3 | The user's CV is reachable from more than one of their own devices without a server. |
| G4 | Nothing is lost. A failed or impossible sync never costs data. |
| G5 | Every feature of the legacy app is carried over. Its `_hist` audit tables are explicitly not — see D15. |
| G6 | The known legacy bugs are fixed, not reproduced. See §9. |
| G7 | The editing experience is materially better than the legacy app. See §8. |
| G8 | The CV can be exported as a PDF or as a Word document, not only printed. See D21, D22. |
| G9 | The existing SQLite database can be imported once, with a documented and repeatable procedure. See §10. |

## 3. Non-goals

Explicitly out of scope **for the initial release**, which is an equivalent tool.
Revisiting any of these means revisiting G1.

- **Multi-user, sharing, or collaboration.** One person, their own devices, their
  own Dropbox.
- **Any server this project operates.** No auth backend, no API, no database
  server, no scheduled jobs.
- **Application-level encryption of the CV data.** Decided with the user: the
  Dropbox App Folder is the trust boundary. The data is exactly as private as the
  Dropbox account behind it. See §11 for what this means.
- **Preserving the SQLite schema.** The shape of the data is preserved; the
  storage engine is not. See §5.
- **A CV generation engine.** No scoring, no tailoring, no job-description
  matching.
- **Rich text.** Stories are plain text with paragraph breaks. No markdown, no
  HTML, no formatting.
- **Native or mobile apps.**
- **PWA / installable.** *Decided (D53):* no manifest, no service worker. Revisitable.
- **Writing-support material.** See §16. Additional reference material to help the
  user write is a later phase and is not designed here.
- **AI-assisted writing.** See §16. A later phase, and the one constraint that
  decides its shape is already knowable.

## 3a. Scope of the initial release

The initial release is **an equivalent tool**: the legacy app's features, with its
bugs fixed and its interface rebuilt. Phases 0–8 get there. Phases 9 and 10 are the
new functionality, and they sit deliberately after the SQLite migration so that the
tool is usable on its own before it grows.

## 4. Current state (what constrains the design)

Extracted from the legacy source at `tmp/cv`. These are facts about the data that
the rewrite MUST account for, not opinions about it.

### 4.1 The schema, after five migrations

`01_init.sql` creates **version 2** (there is no version 1 and no
`02_upgrade_from_1.sql`). Surviving tables at version 5:

| Table | Columns |
| --- | --- |
| `jobs` | `job_id` PK, `creation_date`, `last_update_date`, `start_date` TEXT, `end_date` TEXT, `company`, `job_title`, `responsibilities` BLOB, `job_story` BLOB, `obsolete` INTEGER NOT NULL DEFAULT 0, `questions` boolean |
| `achievements` | `achievement_id` PK, `creation_date`, `last_update_date`, `job_id` INTEGER, `achievement`, `story` TEXT, `obsolete` |
| `awards_edu` | `award_edu_id` PK, `creation_date`, `last_update_date`, `type` TEXT, `date` TEXT, `institution`, `what`, `story` BLOB, `obsolete` |
| `header` | `header_id` PK, `name`, `last_update_date`, `creation_date`, `title`, `email`, `address`, `phone`, `obsolete` |
| `<table>_hist` | mirror of the base columns, plus `hist_id` PK and `hist_creation_date`. **Never read by any query or view — written only. Not migrated (D15).** |
| `db_version` / `db_version_hist` | schema version singleton plus its audit |
| `month_translation` | lookup table, `01`–`12` → `Jan`–`Dec`, plus a sentinel row `(13, '', 'Unknown')` |
| `region` / `region_hist` | seeded with `'domestic'` |
| `responsibilities` / `responsibilities_hist` | **orphaned** — v5 copied their contents into `jobs` and left the tables in place |

Notes that matter:

- **No foreign keys anywhere.** `achievements.job_id` is a plain integer column
  with no `REFERENCES` clause. Integrity is by convention.
- **Dates are `TEXT`.** Job dates are `%Y%m%d` (`20240131`); award and education
  dates are `%Y` (`2024`). Display formatting is done in Python:
  `datetime.strptime(job['start_date'], '%Y%m%d').strftime('%b %Y')`. Anything
  that is not exactly `%Y%m%d` raises `ValueError`.
- **Empty `end_date` means "present"**, and only the empty *string*. A `NULL`
  `end_date` reaches `strptime(None, ...)` and crashes the page.
- **`questions` is a flag, not a type.** `1` means the row is a "question
  category"; anything else (including `NULL` and `0`) means it is a job. The
  partition test is a strict `== 1`.
- **`awards_edu` is one table with a `type` discriminator.** `NULL` type is
  silently coerced to `'award'` at load time.
- **Text bodies are declared `BLOB`** but hold plain text.
- **There are no `updated_at` semantics suitable for merge.** `creation_date` and
  `last_update_date` are `current_timestamp`, so they work, but see §5.3.

### 4.2 What the data model actually means

Reading `db.py:get_full_doc()` and the templates together:

- A **`Job`** is a company + title + date range. It carries `responsibilities` (a
  block of prose) and an optional `job_story`.
- An **`Achievement`** hangs off a Job, and carries an optional `story`. Achievements
  with a `NULL job_id` are attached at read time to the highest-numbered job
  (`select max(job_id) from jobs`) via a `def_job_id` fallback column.
- An **`Award`** or **`Education`** entry is institution + what + year + optional
  story.
- A **`header`** row is a contact block, keyed by `name`. `data.header_selected`
  defaults to `'domestic'`, and the UI toggles between `domestic` and
  `international`. The seeded `region` table contains only `'domestic'`.
- The **`questions` flag** splits Jobs into two lists that render identically,
  except that a question category shows no date range. Its achievements are, in
  substance, interview questions the user has prepared answers for.
- **`story` and `job_story` are interview preparation material, not CV content.**
  They are the long-form "why this role mattered" writing, and the legacy export
  excludes them by default. This is the key to reading the whole model: the
  document holds both the CV you send and the preparation you do before an
  interview, and they are different documents over the same data. See §5.5a.

### 4.2.1 Which entities appear in which document

| | CV | Interview prep |
| --- | --- | --- |
| Contact header | yes | yes |
| Job, Achievement, Award, Education | yes | yes |
| QuestionCategory, Question | no | yes |
| Job.story, Achievement.story, Award.story, Education.story | no | yes |
| Records marked deleted | no | optional |

### 4.3 The user interface, as it is today

One page (`_main.html`) composed of: hamburger menu, header banner, work history,
awards/education, a rule, questions. Every job, achievement, award and education
entry embeds its own collapsed edit form and its own collapsed story panel, so the
DOM holds one form per record before the user has scrolled anywhere. Disclosure is
driven by 22 lines of ES5 that depend on sibling adjacency
(`this.nextElementSibling`), with no `<details>` fallback — with JavaScript
disabled the app is entirely unusable.

Editing navigates to `/cv/editJob?job_id=N`, and saving posts to
`/cv/write?navigateToAnchor=N&action=writeJob`, which redirects to `/?#N`.

The export (`career_mgt_doc.html`) is a separate printable document with its own
class family (`.title_cmd`, `.job_title_cmd`, `.job_resp_cmd`) and hardcodes the
title `CURRICULUM VITAE - Jared Church`.

## 5. Design decisions

### 5.1 Stack

Chosen to match `personal-time-tracker` exactly, so the two projects share
toolchain knowledge, CI shape and review habits.

| Concern | Choice | Note |
| --- | --- | --- |
| Language | TypeScript 6.0.x | Pinned, not `latest`: `typescript-eslint` requires `<6.1.0`. |
| UI | React 19 (function components, hooks only) | No class components, no state library. |
| Build | Vite 8 | `build` is `tsc -b && vite build`. |
| Local storage | IndexedDB via Dexie 4 | Same as the reference; the reference's schema-migration tests are directly reusable. |
| Validation | Zod 4 | One envelope schema serves sync, backup and import. |
| Test | Vitest 5 + jsdom + `fake-indexeddb`; Playwright for e2e smoke | `globals: false`; `TZ` pinned. |
| Lint / format | ESLint 10 + `typescript-eslint` 8 (type-aware) + Prettier 3 | `.prettierrc.json` verbatim from the reference. |
| Dropbox client | **Raw `fetch`, no SDK** | The reference does this; it is four endpoints. |
| DOCX generation | `docx` 9.x | Browser-native and declarative. `docx-templates` was rejected: it needs a template file shipped and parsed as a second asset. |
| Blob download | Native — `URL.createObjectURL` + `<a download>` | No `file-saver`; every target browser does this. |
| Runtime deps | react, react-dom, dexie, zod, docx | Five. Direct-dependency minimalism is a requirement. |

**D1** — The application MUST be a client-side-only SPA. There MUST NOT be a server
component, an API route, or a database outside the browser.

**D2** — The stack MUST match `personal-time-tracker` for anything not listed as a
deliberate difference. Every difference needs a reason recorded in this file.

**D3** — `base` MUST be derived from `package.json#name` with a `VITE_BASE_PATH`
override, and a copy of `index.html` MUST be emitted as `404.html` at build time,
so deep links work on GitHub Pages (which performs no request rewriting).

### 5.2 Storage: a single JSON envelope

SQLite in the browser means shipping a WASM SQLite build and syncing a
multi-megabyte binary whose conflicts are unmergeable. The document is a few
hundred kilobytes of text at most; a JSON document is diffable, reviewable,
mergeable per record, and readable when something goes wrong.

**D4** — The persisted form of the CV MUST be a single JSON envelope. One file,
one schema, three consumers: the sync engine, the local export, and the import
path. There is no separate history artefact — Dropbox's own file revisions are
the history, and they are already there.

**D5** — The envelope MUST be validated with Zod on every read and every write.
Parsing MUST fail closed: a file that does not parse MUST be reported and MUST NOT
be overwritten.

**D6** — Entity objects MUST be `z.looseObject`, not `z.object`. A plain Zod
object strips unknown keys, so a document written by a later build and synced
into an older one would silently lose fields. `looseObject` lets an older build
carry a newer build's file, which is the failure mode that destroys user data.

**D7** — The envelope MUST carry a `schemaVersion` (the document layout version)
and a `formatVersion` (the envelope wrapper version). A reader MUST refuse a
`schemaVersion` newer than it supports rather than interpreting what it does not
understand.

**D8** — The envelope MUST carry a `counts` map, and the reader MUST verify it
against the actual table lengths. This is the half that catches a file truncated
by a quota, an interrupted upload, or a hand edit.

### 5.3 The data model

Every synced entity gets `id`, `updatedAt`, `deletedAt` — the triple that makes
whole-record last-write-wins merge possible (§6.4).

```
Settings    id, updatedAt, deletedAt, activeProfileId | null
Profile     id, updatedAt, deletedAt, name,          // user-chosen, e.g. 'Domestic', 'NZ'
            title, email, address, phone
Job         id, updatedAt, deletedAt,
            startDate 'YYYY-MM-DD', endDate 'YYYY-MM-DD' | null,   null = present
            company, jobTitle, responsibilities, story
Achievement id, updatedAt, deletedAt, jobId, achievement, story
Award       id, updatedAt, deletedAt, year, institution, what, story
Education   id, updatedAt, deletedAt, year, institution, what, story
QuestionCategory id, updatedAt, deletedAt, title, story
Question        id, updatedAt, deletedAt, categoryId, question, answer
```

Changes from the legacy shape, each of which is a judgement call rather than a bug
fix:

- **The `questions` flag becomes two real entities.** *Decided.* In the legacy
  schema a "question category" is a `jobs` row with `questions = 1`, and a
  question is an `achievements` row hanging off it — so a question carries a
  `company`, a `job_title` and two date columns it can never use, and both sections
  are forced through the same form and the same `?job_id=` dropdown. `QuestionCategory`
  and `Question` drop all of that. `Job` therefore loses its `kind` field entirely:
  it means "a job", with nothing to discriminate.
- **`YYYYMMDD` text → ISO `YYYY-MM-DD`.** *Decided: full date precision.* The
  legacy data already holds a day, so storing it loses nothing on migration, and
  the form gets a real date picker instead of a free-text field demanding eight
  digits. The document continues to **display** `Jan 2024` — that is a
  presentation choice (D17), not a storage one, and it matches CV convention.
- **`Award` and `Education` become two entities**, rather than one table with a
  `type` column — *decided*. They are never edited together and they sort
  separately. But the **export renders them as a single combined table**, sorted by
  year, because that is what the document needs to look like (D16). The separation
  is a storage decision; the combined table is a presentation decision, and the two
  are deliberately independent.
- **`obsolete` → `deletedAt`.** Same intent — hide from the document, keep the
  record — but it participates in merge instead of needing special handling, and
  it is distinguishable from "was never here".
- **`Achievement.jobId` is required, not nullable.** The legacy `def_job_id`
  fallback exists because the column had no constraint and rows were inserted with
  `NULL`. With a required field the fallback cannot be reached, so the `KeyError`
  path in §9 disappears rather than being patched.
- **`Profile` becomes a user-managed list with one active selection.** *Decided.*
  The legacy `header` table was keyed by a fixed region name seeded with only
  `'domestic'`, and had no edit UI at all (`/cv/editHeader` returns the string
  `"not defined"` — L10). The rewrite lets the user define any number of profiles,
  name them freely, and choose which one the document header uses. `Settings.activeProfileId`
  records the selection. The legacy toggle is gone; the profile picker replaces it.

**D9** — No entity may carry a field that nothing reads. The legacy `db.py.__main__`
block and the `<pre>` block of unimplemented CLI verbs in `menu.html` are dropped,
not ported.

### 5.4 Presentation

**D10** — Editing MUST offer **two** surfaces, both kept:

- **One page, in context** (`/`) — the whole document in document order, with each
  record's form opening in place beneath it. This is the legacy app's model, it
  is the default page, and it is the primary surface, because revising an existing
  CV means reading the thing while you change it. Each row shows enough to
  recognise the record without opening it — company and title, dates, and for a
  job the responsibilities — so scanning the document does not mean opening every
  record. That preview is clamped in CSS and never truncated in storage (D31).
- **Per-record routes** (`#/jobs/:id/edit`) — for arriving at one thing by link,
  from a search result or a "fix this" link out of the fit report.

There are no per-entity **list** routes for anything the edit-all page already
holds in document order: jobs, achievements, awards and education are all listed,
created and edited there, so a list page for any of them was a second way to do
the same thing and one more surface to keep in step. Profiles and the two question
lists keep theirs, since neither is a section of the edit-all page. The header
reaches the career content as "Work history", which is what `/` now is.

Both render the same `RecordForm`, so they cannot drift apart. The form MUST be
mounted only while its disclosure is open, and MUST NOT be rendered for every
record at page load — the legacy app did that, so a CV with thirty achievements
shipped thirty forms and the browser rendered all of them before the user had
scrolled anywhere.

MUST NOT show a count of a parent's children beside the button that adds them.
The children are the list; the number is the same information twice, and it costs
a line of height on every row. The control that adds a child sits beside the
parent's own Edit button, because that is where the user is already looking for
it, with the form opening in the child's place beneath.

**D11** — The exported CV MUST share one stylesheet with the editor, using a
prefix convention (as the legacy app did with `*_cmd` suffixes), rather than being
a separate template tree.

**D12** — The document title MUST come from the data. The hardcoded
`CURRICULUM VITAE - Jared Church` MUST NOT survive.

**D13** — Untrusted text MUST reach the DOM as a value, never as markup. Stories
MUST render as text nodes with paragraph elements, never via `dangerouslySetInnerHTML`.
This is the root cause of the legacy v4 data repair and MUST NOT recur.

**D14** — The app MUST ship a light and a dark theme, following the system
preference by default, with a pre-paint bootstrap in `index.html` so the theme is
correct on first paint.

**D15** — There MUST be no history table, no revision log, and no audit artefact in
the application. The legacy `_hist` tables are not carried over. Dropbox's own file
revisions are the undo history, and the local export is the backup; a third copy
inside the document is redundant and would double the size of every sync for no
feature that has ever existed.

**D16** — The export MUST render `Award` and `Education` records in a **single
combined table**, sorted by year and then by institution, because that is the shape
a CV uses. The two remain separate entities in storage and separate forms in the
editor; only the document view combines them. The combined table MUST be sorted and
rendered identically in the browser view and in print, or the printed CV will not
match the screen.

**D17** — Job dates MUST be **stored at full precision** and **displayed at month
precision** (`Jan 2024`), matching CV convention and the legacy document's own
output. The day is available in the edit form and is carried through sync and
export, but it is not printed on the document unless both dates fall in the same
month, in which case the day range is shown.

**D18** — Profiles MUST be creatable, editable and deletable, and exactly one MUST
be selectable as active for the document header. Deleting the active profile MUST
require choosing a replacement or explicitly having none. This closes L10, which the
legacy app leaves as a route returning `"not defined"`.

**D19** — The questions section MUST be modelled as its own two entities,
`QuestionCategory` and `Question`, and MUST NOT be carried in the `Job` /
`Achievement` tables behind a flag. In the legacy schema it is exactly that: a
`jobs` row with `questions = 1` whose achievements are questions, which is why
every question is forced through a company field, a title field, two date fields
and a parent-job dropdown it cannot use.

**D20** — A `Question` MUST belong to exactly one `QuestionCategory`, and a
`QuestionCategory` MAY carry its own `story` (the legacy `job_story` on a
`questions = 1` row), which is what the legacy UI shows as the category's story
panel.

**D21** — Export MUST be a set of interchangeable exporters behind one interface,
so adding a format is a new module and not a change to the export view:

```ts
export interface DocumentExporter {
  readonly id: string
  readonly label: string
  /** The MIME type recorded on the generated blob. */
  readonly mediaType: string
  readonly fileExtension: string
  /**
   * Build the document from the same resolved view model the screen and print
   * views use, so every format renders from one interpretation of the data.
   */
  build(model: DocumentModel, options: ExportOptions): Promise<Blob>
}
```

**D22** — Two export formats MUST ship: **PDF via the browser print dialog** and
**`.docx` for Microsoft Word**. The PDF is not generated — a print view with a
print stylesheet is rendered and the user chooses "Save as PDF", which is what the
reference project does and what keeps the PDF dependency-free. The `.docx` is
generated client-side with `docx` 9.x, which is browser-native and declarative.

**D23** — Additional formats — Google Docs, OpenDocument, Markdown, plain text —
MAY be added later as further `DocumentExporter` implementations. They MUST NOT be
built now. This is recorded so the interface is shaped for them, not so they get
built.

**D48** — The `.docx` exporter MUST produce a **natively styled Word document**,
not a picture of the on-screen one. *Decided.* That means real Word heading levels
(so the navigation pane works and the user can restructure), a real table for the
combined awards/education entries (D16), and normal paragraphs throughout.

Reproducing the screen layout closely was rejected: it produces a document that
looks right until the user changes anything, at which point it falls apart, and it
discards the structure that is the main reason to ask for Word in the first place.

**D49** — Every format MUST receive the **same `DocumentModel`**, with the same
preset and the same overrides. *Decided.* A CV is a CV whether it is a PDF or a
`.docx`; a format that honours a different set of options is a format that
silently produces a different document from the same settings. Word can do things
PDF cannot — real bullet lists, document properties — and those are rendering
concerns inside one exporter, not differences in what the document contains.

**D24** — All exporters MUST consume one `DocumentModel`: the resolved, ordered,
option-filtered view of the document (active profile, section order, whether
stories/questions/deleted records are included). No exporter may re-derive that
from raw entities, or the formats drift apart.

**D25** — The Dropbox client id MUST be selected by host between **two** Dropbox
apps — development and production — so a locally-served dev build cannot write to
the production document. The selection MUST NOT consult `localStorage` (SY10) and
MUST be the same function that renders the environment badge, so the badge and the
sync target cannot disagree about which environment this is.

**D26** — The app MUST NOT be gated. The Pages URL is public, and this is
accepted rather than mitigated: the shell contains no data, the document lives in
the user's browser and their Dropbox, and the OAuth token never leaves their
browser. A URL passphrase would protect the shell — which is empty — while putting
a secret in browser history.

### 5.5 Print typography and page fitting

The goal is a document that fits on one page. The mechanism matters, so it is
spelled out.

**D27** — Print typography MUST be **user-controlled and never automatically
fitted**. The app MUST NOT shrink text to make content fit. Auto-fitting makes the
output non-deterministic — the same data exports differently depending on what else
is in the document — and it pushes the problem onto legibility, which is the one
thing a printed CV cannot afford.

**D28** — The user MUST be able to adjust the print type scale, in discrete steps,
from a compact setting to a comfortable one. *Decided: the setting is part of the
document* (`Settings`), so it syncs and follows the user between devices — not a
per-device preference. It applies to the screen document view and to print
together, so what is measured is what is printed. A per-device setting would mean
retuning every device, and would leave the fit report measuring a scale that is not
the one being printed.

**D41** — **Page size MUST be a document setting**, with **A4 as the default**.
*Decided.* It belongs with the type scale for the same reason: it is a property of
the document, and a CV tuned to fit A4 will print differently on a Letter page.

**D42** — The supported page sizes MUST be A4, US Letter and Legal. Anything larger
is not a CV, and anything smaller is not paper. Portrait only.

**D43** — The document MUST declare its page size to the print engine
(`@page { size: … }`), **and the app MUST tell the user that the browser's print
dialog also needs the paper size set to match.** This is the detail that silently
breaks the feature: browsers default the print dialog to "the printer's default"
and many users never look at it, so the document prints correctly onto A4 while
the CSS believes it is onto Letter — margins wrong, page breaks wrong, and the fit
report describing something that was never printed. The app cannot detect or
correct what the dialog does; it can only say so, before printing.

**D44** — The `.docx` exporter MUST set Word's page setup from the same setting,
so a Word export is laid out on the same paper as the print output. A document
tuned to fit one A4 page and exported to Letter is the same bug in a different
place.

**D45** — The fit report (D32) MUST be relative to the selected page size, and
MUST be recomputed when the page size, the type scale or the density changes.
Every one of those changes the answer, so a stale fit report is worse than none.

**D50** — The app MUST NOT attempt to detect the printer's paper size, and MUST
NOT remember a previously chosen one. *Decided.* Browsers do not expose it, so
detection is a guess wearing a feature's clothes, and remembering bakes in an
assumption that is wrong for a different printer or a one-off print. Instead the
page size MUST be shown prominently in the print steps with an explicit instruction
to match it in the print dialog (D43).

**D52** — PDF export is print-only, including on mobile. *Decided.* Both iOS and
Android have a native share-to-print path that produces a PDF, so a separate
save-to-PDF button would be a second, worse implementation of something the OS
already does well.

**D53** — The app MUST NOT be a PWA and MUST NOT be installable. *Decided, with a
deliberate preference for lower effort.* A bookmark delivers most of what
installing would — and iOS already permits adding the site to the home screen
without a service worker — while a manifest and a service worker bring a cache
invalidation problem and a "which version is this installed copy running" problem
that neither the reference project nor this one needs. Sync already makes the
document available on a phone; the app simply is not tuned for one. This is a
decision to revisit, not a position: if desktop-only use stops being true, this is
the first thing to reopen.

**D46** — Fit MUST be defined in **points, not pixels**. A page measured in CSS
pixels at an assumed 96 dpi is an estimate of an estimate; millimetres and points
are what the paper, the margins and Word's page setup are actually expressed in,
and mixing units is where a layout silently drifts by a few percent.

**D47** — The fit report MUST be computed by **measuring the rendered document in
the DOM** and MUST be **labelled an estimate**. *Decided.* Browsers expose no API
for paginated layout, so there is no exact option to choose — anything claiming an
exact page count is guessing. Measuring what is on screen against the page box in
points (D46) catches the case that matters, a CV that is slightly over one page,
and being wrong by a line is a far smaller failure than an auto-fitter silently
producing an illegible page.

The alternative — generating a real PDF purely to measure it — was rejected: it
means shipping a PDF generator, which D22 rules out on the grounds of it being the
largest dependency in the project for a single-user tool.

**D29** — **Density MUST be a separate control from font size.** Density changes
margins, line-height and vertical spacing — the things that consume page height
without reducing legibility. Fitting is overwhelmingly a spacing problem, not a
type-size problem, and separating the two means the user can reclaim a page
without making the text harder to read.

**D30** — There MUST be a **floor** below which the app will not shrink anything,
whatever the user asks for. Past the floor the app says the document does not fit
and what to shorten, rather than complying with an illegible result.

**D31** — The app MUST NOT truncate text to achieve a fit. A shortened achievement
is a different and worse achievement, and the user cannot tell from the print
preview that it happened.

**D32** — The app MUST report the **fit**, in the document view and before print:

- an estimated page count, and whether it exceeds the target;
- per-record flags for text that will wrap to more lines than the target — an
  achievement that will run to four lines when the document's norm is one;
- a specific list of what to shorten, not a general warning.

This is the mechanism that actually achieves a single page: it tells the user
which four bullets to rewrite, which is a writing problem the user can solve, rather
than a typography problem the app should not solve for them.

**D33** — Page breaks MUST be controlled explicitly: no job, achievement or
education block may be split across a page boundary, and headings MUST NOT be
orphaned at the foot of a page. The common failure in a dense CV is a company name
at the bottom of one page and its achievements at the top of the next.

**D34** — The print layout MUST be a **single column** with no text boxes, no
multi-column layouts and no tables used for positioning. Applicant tracking systems
parse the text stream, and layout tricks are the most common cause of a CV parsing
badly. The awards/education combined table (D16) is real tabular data and is
allowed; using tables to align a name and a date in the header is not.

**D35** — The target page count MUST be a **per-document setting**, not a constant.
One page is the default for the CV document (§5.5a); interview preparation is
allowed to run to any length and is not measured against a target at all.

### 5.5a Two documents, not one document with switches

The legacy app presents the document as a single view with three checkboxes —
"include stories", "include questions", "include obsolete" — all unticked by
default. Reading what those three things actually are, they are not three options.
They separate two documents that happen to be rendered by the same template:

- **The CV.** What is sent to an employer. Work history, achievements, awards,
  education and the contact header. No stories, no interview questions, nothing
  deleted. *This is the document with a one-page target.*
- **Interview preparation.** Everything, including the stories that explain why a
  role mattered and the prepared answers to questions likely to be asked. Long.
  There is no reason for this to fit on a page, and compressing it would destroy
  the reason it exists.

The legacy checkboxes let you produce neither cleanly, because a CV that
accidentally includes stories and a prep document that accidentally omits deleted
records are both wrong, and it is not obvious which one you are holding.

**D36** — The document MUST be selectable as one of two named presets — **CV** and
**Interview preparation** — and the presets MUST be one selection, not a set of
independent switches to get wrong. The CV preset is the default.

**D37** — Each preset MUST have a fixed, documented content set:

| | CV | Interview preparation |
| --- | --- | --- |
| Contact header | yes | yes |
| Work history | yes | yes |
| Achievements | yes | yes |
| Awards / education | yes (one combined table) | yes (one combined table) |
| Question categories | no | yes |
| Stories | no | yes |
| Deleted records | no | yes (on request) |
| Page target | one | none |

**D38** — The granular include/exclude toggles MUST remain available, so a CV with
stories in it is still possible — but they MUST be presented as a deviation from
the selected preset, never as the primary control. Selecting "Interview
preparation" and then unticking questions is a legitimate thing to want; having to
untick three boxes to *get* the CV is not.

**D39** — Every exporter MUST accept the preset as input and MUST NOT decide for
itself what a CV is. A `.docx` interview-prep document and a `.docx` CV are the
same exporter with different inputs, and the difference MUST be visible to the user
before they export, not discovered afterwards.

**D40** — The one-page target and the fit diagnostics (D32) MUST apply to the CV
preset only. Interview preparation MUST NOT be measured against a page target, and
MUST NOT show a fit warning — a prep document that is eight pages long is working
correctly.

### 5.5b Document templates

The two presets (D36) decide *what* is in the document. They do not decide what it
looks like, and everything about that is currently compiled into one stylesheet
that the user cannot reach. A CV that is right for one job is wrong for the next:
the section order, which sections appear at all, the heading wording, the margins
and the type scale are all fixed, and a user who wants "Experience" above
"Education", or no awards section, or a two-page document for a senior role, has no
way to get it.

The legacy app had none of this either — its export styling is a second class
family (§9, U9, U15), hand-aligned pixel columns with no control at all. So this
is not a gap the rewrite inherited and left; it is a gap it should close, but only
after the part that already works is finished and shipped.

**Nothing here is built yet.** What follows is the shape, so the decision is not
made twice: once in conversation and once in code.

#### 5.5b.1 What a template is

A template is a named set of document settings, stored in the same envelope as
everything else so it syncs between devices. It is not a separate document type,
and not a file the user imports — it is settings with a name, which means choosing
one is choosing values the document already has.

**D54** — The app MUST ship at least one template, and its name MUST be the one the
current document produces. An existing user's first load MUST look exactly like
their previous load; a template is a choice, never a surprise on upgrade.

**D55** — A template MUST be a complete, valid set of document settings. A partial
template MUST be rejected on write, not merged into whatever the current settings
happen to be. Two devices editing templates must converge by last-write-wins like
everything else, and a half-written template is the one state that cannot be
recovered from.

**D56** — Switching templates MUST NOT touch a record. A template is a set of
settings; the achievements, jobs and stories are not part of it. This is the line
that keeps the feature from becoming a second document type, and it is drawn here
because it is the obvious thing to erode.

#### 5.5b.2 What a template may set, and what it may not

The settings that exist today are page size, type scale and density (D28, D41–D44).
A template may set those, and the section ordering and the section list.

**D57** — A template MAY set: page size, type scale, density, the order of the
document's sections, which sections are included, and the heading text for each
section. These are all either already stored or small additions to the envelope.

**D58** — A template MUST NOT carry CSS, HTML, or any executable content, and MUST
NOT accept a stylesheet as a string. The reason is specific: a template is
synced through Dropbox and shared between devices by a mechanism with no
authentication (§11, SEC2, D26). A template that could carry CSS could restyle the
app as well as the document, and the user cannot review a stylesheet they were
never shown. Settings that compose are the design; code that formats is not.

**D59** — The preset (D36) MUST remain orthogonal to the template. The template
decides the shape; the preset decides the content. Choosing a template MUST NOT
silently change a CV into an interview-prep document, and changing preset MUST NOT
change the template.

#### 5.5b.3 Interaction

**D60** — The template selector MUST sit in the same right-hand rail as the preset
and profile selectors, so the three choices that decide a document are in one
place. It MUST show what is different about each template before it is chosen — a
one-line summary of the page size, the section order and the sections it adds or
drops — because "International" tells the user nothing about what they will get.

**D61** — "Edit current" MUST produce a new template rather than modifying a
built-in one in place. Built-in templates are not the user's to change, and a
built-in that changed silently would make "the same template" mean different things
on two devices.

**D62** — A template MUST be deletable only if it is not built-in, and the delete
MUST offer undo in the same way a record delete does (U5). Losing a template is
losing settings, and settings have no other copy — a document already sent to an
employer cannot be regenerated from the app.

#### 5.5b.4 Why this is deferred rather than dropped

The type scale, density and page size already exist and already sync. Everything
above is the *selection* of settings and the section structure — genuinely useful,
genuinely deferred, and not needed for the app to be correct.

It sits after the first production release (§13, Phase 7) and alongside Phase 9's
writing support rather than before them, because both of those change what the
document contains, and designing a template format before the content has settled
means designing it twice.

## 6. Cross-device sync

Dropbox is the only provider. The design MUST NOT bake Dropbox's API shape into
the rest of the app, so a second provider can be added without touching the sync
engine. This is the layering rule from `personal-time-tracker`, and it is copied
verbatim in intent.

### 6.1 Layering

```
sync/provider.ts        SyncProvider interface + SyncError taxonomy
sync/appKey.ts          client-id selection by host
sync/redirect.ts        the single definition of the OAuth redirect URI
sync/oauthCallback.ts   runs once at startup, before render
sync/engine.ts          runSync() + pushWithRetry()
sync/scheduler.ts       triggers, debounce, retries, status
sync/dropbox/           the only code that knows Dropbox exists
domain/merge.ts         pure merge — the highest-risk code in the project
```

`SyncProvider`:

```ts
export interface RemoteFile {
  body: string
  /** Opaque provider revision. Detects a concurrent write so it is merged, not clobbered. */
  rev: string
}

export interface SyncProvider {
  readonly id: string
  /** Idempotent. Runs at the start of every cycle. */
  ensureAuth(): Promise<void>
  /** Discard credentials. Local data MUST be untouched. */
  signOut(): Promise<void>
  pull(path: string): Promise<RemoteFile | null>
  push(path: string, body: string, expectedRev: string | null): Promise<{ rev: string }>
}
```

`SyncErrorKind` is `'auth' | 'scope-missing' | 'rate-limited' | 'not-found' |
'conflict' | 'network' | 'unknown'`. Only `rate-limited`, `network` and `conflict`
are retryable. `scope-missing` is split out from `auth` specifically so the
recovery is mechanical — discard the credential and offer Connect — rather than
guessed at from an error message.

### 6.2 Authentication

Browser-only OAuth against Dropbox, which supports PKCE for public clients.

**SY1** — The app MUST be **local-first**. IndexedDB is the source of truth. The
remote is a convenience and a backup, never a prerequisite.

**SY2** — No user action MUST be blocked on the network. Every sync MUST be
fire-and-forget from the user's perspective.

**SY3** — A failed or impossible sync MUST NOT cause data loss and MUST NOT
disable or degrade any feature. Offline is a normal state.

**SY4** — PKCE with `code_challenge_method=S256`. `plain` MUST NOT be used.

**SY5** — The authorize request MUST include `token_access_type=offline`. Dropbox
documents this as a requirement, not a default; without it no refresh token is
returned at all and the connection dies after four hours.

**SY6** — The authorize request MUST NOT include a `scope` parameter. Permissions
are granted in the Dropbox App Console, which is then the single source of truth.
Requesting an explicit subset makes the app fail to start at all if console and
code disagree by one scope.

**SY7** — The PKCE verifier MUST be persisted in `sessionStorage` with a
10-minute TTL, not held only in memory. The OAuth redirect is a full page
navigation; anything held only in memory is gone when the code returns.

**SY8** — The redirect query string MUST be cleared with `history.replaceState`
**before** the token exchange. The authorisation code is single-use, and a refresh
during the exchange would attempt to redeem it twice.

**SY9** — Token refresh MUST distinguish a *rejected* refresh token from an
*unreachable* token endpoint. A rejection means the credential is dead and MUST be
discarded; unreachability means the network is down and MUST be retried. Collapsing
these signs the user out during a network blip.

**SY10** — The client id MUST be selected by **host**, not by build type and not
from `localStorage`. A key saved in the browser pairs with whichever redirect URI
that other app registered, and Dropbox rejects it with `invalid_redirect_uri` while
naming nothing useful.

**SY11** — The app MUST NOT possess an OAuth client secret. Anything in a
`VITE_`-prefixed variable is bundled into shipped JavaScript and is public.

### 6.3 The remote file

**SY12** — One file: `career-management-document.json`, relative to the Dropbox App
Folder (so `/apps/<app name>/career-management-document.json`). One file means one
atomic unit: there is no cross-file consistency problem, and a sync either lands
whole or not at all.

**SY13** — Writes MUST use `mode: { '.tag': 'update', update: rev }` when a
revision is known and `mode: 'overwrite'` on first run. The revision mismatch
rejected by Dropbox **is** the conflict detection; there is no client-side clock or
content hashing.

**SY14** — Uploads MUST set `autorename: false` (never create a duplicate on
conflict), `mute: true` (no "edited a file" notifications), and
`strict_conflict: true` (a revision mismatch against a since-deleted file must not
pass silently).

**SY15** — Scopes MUST be `files.content.read` and `files.content.write` and
nothing else. Dropbox App Folder access MUST be selected.

### 6.4 Merge

**SY16** — Merge MUST be a pure function of two snapshots: no I/O, no clock reads,
no framework imports, so it can be property-tested directly.

**SY17** — Merge MUST be a **union** by `id`. Nothing present on either side is
ever dropped.

**SY18** — Conflicts MUST be resolved by whole-record last-write-wins on
`updatedAt`, never field-by-field. Field-level merge can synthesise a record that
never existed on either device.

**SY19** — An exact `updatedAt` tie MUST be broken by comparing canonical
serialisations, so that every device independently arrives at the same answer.
Plain `JSON.stringify` is not deterministic — key order follows insertion order,
which differs between two devices that built the same record by different routes.

**SY20** — `deletedAt` MUST be an ordinary field, resolved by the same
last-write-wins rule as an edit. Tombstones MUST be retained in the output so a
device offline for a month does not resurrect deletions made elsewhere.

**D51** — Tombstones MUST be kept **forever**; they MUST NOT be pruned by age or by
document size. *Decided.* The tombstone is the entire mechanism that stops a device
which has been offline for a month from resurrecting something you deleted, and
dropping it reopens exactly that failure. They cost a few bytes each against a
document that is never large. Undo is a separate question and is answered by
Dropbox's own file revisions, not by the application.

**SY21** — The output MUST be sorted by `id` so the bytes are identical on every
device.

**SY22** — `schemaVersion` in the merged result MUST be the maximum of the two
inputs, never the minimum.

### 6.5 The cycle

**SY23** — Sync MUST run on: app open, a local write (debounced 5 s), the tab
becoming visible, `pagehide`, and a manual button. There MUST NOT be background
polling — there is no inbound push path, so a poll produces only empty cycles and
keeps the device awake.

**SY24** — The local-write trigger MUST be the storage layer's revision counter,
not a call from each view that happens to make the change. With the trigger
supplied from outside, every write path has to remember to call it, none do, and
the behaviour is untestable in production while its tests pass.

**SY25** — Sync cycles MUST NOT overlap. One queued cycle is allowed; parallel
cycles are not.

**SY26** — Whether to publish MUST be decided by **content** — comparing the
canonical serialisation of the merged snapshot against the remote snapshot — not
by comparing revisions. A local-only change leaves the remote revision untouched,
so revision comparison concludes there is nothing to do and local edits never
reach Dropbox at all.

**SY27** — On a push conflict the engine MUST re-pull, re-read local, re-merge and
push against the fresh revision. It MUST NOT retry the same push, and it MUST
re-read local rather than reuse the snapshot the cycle started with, or a save made
during the round trip would be neither merged nor pushed while the UI reported
success.

**SY28** — Transient failures MUST be retried with backoff (5 s, 30 s, 120 s) and
bounded. `auth`, `scope-missing` and `not-found` MUST NOT be retried; waiting
cannot fix them.

**SY29** — A dropped token MUST discard the credential and offer to reconnect,
rather than leaving the UI showing a green "synced" for a connection that no longer
exists.

**SY30** — The sync and backup formats MUST be the same envelope. A separate sync
format is a second schema to maintain and it will drift.

**SY31** — The envelope MUST NOT contain OAuth credentials. A backup is the kind of
file people email around.

### 6.6 Dropbox app setup (prerequisite, per your instruction)

Recorded as a task rather than assumed done. **Two apps are created — development
and production** (D25), selected by host at runtime.

For each app (replace `<app>` with `development` and `production`):

1. Create an app at <https://www.dropbox.com/developers/apps> → **Scoped access** →
   **App folder**.
2. Permissions → Files and folders: tick **files.content.read** and
   **files.content.write** only. Nothing else.
3. OAuth → **Redirect URIs** → add the deployed URL,
   `https://air-ltd.github.io/career-management/` (trailing slash required;
   `BASE_URL` carries it, and a mismatch reports only `invalid_redirect_uri`), and
   `http://localhost:5173/` for the development app so `scripts/run.sh` can
   connect (SY34).
4. Copy the **App key**. This is the OAuth client id and it is public.
5. Put it in `.env` as `VITE_DROPBOX_APP_KEY_PRODUCTION=` (and
   `VITE_DROPBOX_APP_KEY_DEVELOPMENT=` for the dev app).
6. Never put an **App secret** anywhere near a `VITE_` variable. This app never
   needs one.

**SY32** — The host→environment mapping MUST be exact. The production origin is
matched explicitly; **every other host, including `localhost` and
`127.0.0.1`, MUST resolve to development.** A build served anywhere unexpected
defaulting to production is the dangerous direction, and the reference project's
`environmentForHost` is the precedent.

**SY33** — The app MUST display which environment it is talking to, using the
*same* function that selects the app key. Two answers to "is this production" is
how one of them goes stale, and a dev build pointed at production Dropbox is the
failure that matters.

**SY34** — The redirect URI sent in the authorisation request MUST be derived from
`window.location.origin` plus `import.meta.env.BASE_URL`, so the app always asks
for the origin it is actually being served from. **Every origin that will ever
host a development session must be registered in the development app's console
entry** — `http://localhost:5173/` at minimum. Dropbox requires an exact match
and reports a mismatch only as `invalid_redirect_uri`, which names nothing useful.
This includes the local dev server: a development build served from localhost is
still a real OAuth client and still needs its own registered redirect URI.

**DEP2** — The base path MUST come from `VITE_BASE_PATH ?? '/' + packageName + '/'`.

## 10. Migrating the existing SQLite database

**One-off, run once.** Originally deferred until after the first production
release; written early at your instruction once the real database was in hand. The
deferral was sound and the reversal is deliberate — see Phase 8 in §13.

The conversion is done by putting the resulting file into the Dropbox app folder as
`career-management-document.json`, which is the same name the app reads
(`src/sync/dropbox/config.ts`). The sync engine validates it through `parseEnvelope`
before writing anything (`src/sync/engine.ts`), so MIG8 is satisfied by the path
that already exists rather than by an import screen that does not.

### 10.1 Approach

A Node CLI script, `scripts/migrate-sqlite.ts`, run on the user's machine against a
copy of `career_management.sqlite3`. It emits an envelope JSON file, which is then
imported through the app's own import path.

**MIG1** — The migration MUST be a script in the repository, not a mode of the
application. Nothing about SQLite ships in the browser bundle.

**MIG2** — The script MUST emit the **same envelope** the app writes. There MUST NOT
be a second, conversion-shaped format. The script's job is to produce a valid
envelope by another route.

**MIG3** — The script MUST be idempotent and non-destructive. It MUST open the
source database read-only and MUST NOT modify it.

**MIG4** — The script MUST print a summary — row counts per table, records skipped,
and anything it could not interpret — and MUST exit non-zero if anything was lost.

### 10.2 Reading the source

Node 24 ships `node:sqlite`, so this needs no native dependency. If that proves
awkward, `better-sqlite3` is acceptable as a **dev**Dependency.

**MIG5** — The script MUST read only the tables that carry content: `jobs`,
`achievements`, `awards_edu` and `header`. It MUST NOT attempt to migrate
`db_version`, `month_translation`, `region`, any `_hist` table, or the orphaned
`responsibilities` tables (L17).

### 10.3 The transformations

Each of these is a place where the rewrite's data model differs from SQLite, and
each MUST have a test.

| From | To | Rule |
| --- | --- | --- |
| `job_id` INTEGER | `Job.id` | Preserve the integer as a string id. Stable across the migration and across the merge. |
| `jobs.questions = 0` or `NULL` | `Job` | The ordinary case. |
| `jobs.questions = 1` | `QuestionCategory` | `company` → `title`, `job_story` → `story`. `job_title` and both dates have no equivalent and are discarded — see D19. |
| `achievements` whose parent is a `questions = 1` job | `Question` | `achievement` → `question`, `story` → `answer`. |
| `achievements` whose parent is a normal job | `Achievement` | Unchanged. |
| `start_date` `'20240131'` | `startDate '2024-01-31'` | Parse as `%Y%m%d`, re-emit as ISO. A value that does not parse is reported, not guessed. |
| `end_date` `''` or `NULL` | `endDate: null` | Both mean "present". Fixes L3. |
| `awards_edu.type` `'award'`/`'education'`/`NULL` | `Award` / `Education` / reported | `NULL` becomes `Education` **only if** the `what` text matches an education pattern, otherwise it is reported and defaulted to `Award`. L13 must not be reproduced as a silent default. |
| `awards_edu.date` `'2024'` | `year: 2024` | |
| `obsolete` 1/0/`NULL` | `deletedAt: <iso> \| null` | No reliable timestamp exists for the original edit, so the migration run's timestamp is used. Documented as a known imprecision. |
| `creation_date`, `last_update_date` | `updatedAt` | `last_update_date` wins. It is ISO-ish SQLite `current_timestamp` text; parse defensively. |
| `achievements.job_id IS NULL` | attach to the highest-numbered job | The `def_job_id` fallback, made explicit at migration time rather than at every read. |
| `&amp;` `&#039;` `&quot;` `&#37;` `&gt;` in text columns | decoded characters | This is the corruption that schema migration v4 repaired. The migration MUST decode it, because L6 means the corruption was still being reintroduced. |
| `header.name` `'domestic'` / `'international'` | `Profile.name` | Both rows become profiles, keeping their names as given. `Settings.activeProfileId` is set to the `domestic` one, matching the legacy default. |

**MIG6** — The script MUST decode HTML entities in text columns. A CV containing
`Jared &amp; Church` is a corrupted CV, and the legacy app created that text.

**MIG7** — Anything the script cannot interpret MUST be reported on stdout and in
a sidecar report file, and MUST cause a non-zero exit. A migration that silently
drops records is worse than one that fails.

### 10.4 Verification

**MIG8** — The import path MUST validate the emitted envelope against the Zod schema
before writing anything, exactly as it validates any other import.

**MIG9** — After import, the app MUST show the same record counts the script
reported. The user checks this; the docs MUST say to.

**MIG10** — The legacy app MUST remain runnable until the user confirms the import.
The legacy database is the backup.

### 10.5 What is deliberately not migrated

- `db_version` / `db_version_hist` — schema bookkeeping, meaningless elsewhere.
- Every `_hist` table — written but never read (D15).
- `month_translation` — a lookup table for a `strftime` the rewrite does not do.
- `region` — seeded with one row and superseded by `Profile.name`.
- `responsibilities` / `responsibilities_hist` — orphaned (L17). If the user wants
  them, they are in the legacy database still.

## 11. Privacy and security

**SEC1** — The app MUST talk to exactly two third-party origins:
`https://api.dropboxapi.com` and `https://content.dropboxapi.com`. The CSP
`connect-src` MUST list nothing else.

**SEC2** — The CV data MUST NOT be encrypted by the app. Decided: the Dropbox App
Folder is the trust boundary. **This means the CV is readable by anyone with access
to the Dropbox account, and by Dropbox itself.** The alternative — a passphrase and
AES-GCM, which the reference project's design notes show is entirely feasible — is
recorded here as a rejected alternative, not as an oversight.

**SEC3** — The GitHub Pages URL is public and unauthenticated, and by D26 this is
accepted rather than mitigated. Anyone with the URL can load the app shell. The
data is not exposed by this, because the data lives in the browser and in the
user's Dropbox, and the OAuth token is in the user's browser only — but the app
MUST NOT ever commit data to the repository, and MUST NOT read anything from the
URL that could carry document content.

**SEC4** — The OAuth token MUST be stored in IndexedDB via the reference's opaque
`TokenStore`, never in `localStorage` (which is readable by any script on the
origin) and never in the URL.

**SEC5** — A `check:secrets` script MUST run in CI and fail the build if a
credential-shaped string reaches the bundle. A `VITE_`-prefixed variable is public
by definition.

**SEC6** — Untrusted text MUST reach the DOM as a value, never as markup (D13).

**Built ahead of the gate, at your instruction**, once the real

Recorded so the reversal is visible rather than quietly folded in:

- `scripts/migrate-sqlite.ts` (§10)
- A fixture SQLite database built from the legacy schema, committed as a test input
- Tests for every transformation in the §10.3 table, including the ones with no
  example in the real database (malformed dates, `NULL` types)

**Gate:** the fixture database migrates to an envelope that imports cleanly, with
identical record counts; and a second run over the same input produces a
byte-identical envelope.

**Met.** The gate is a test, not a claim: `scripts/migrate/migrate.test.ts` runs
the real CLI over the committed fixture and asserts the counts, that every
migrated record passes `narrowTables`, and that two runs are byte-identical.

The byte-identical property is why the envelope is dated from the **newest
timestamp in the source database** rather than the moment the script ran (MIG11).
`exportedAt` is part of the file, so a clock read would make two runs differ for no
reason — and dating the document as of the last real edit is truer than dating it
as of a conversion the user may rerun months later.

**MIG11** — The clock the envelope is dated with MUST come from the source
database's newest timestamp, and MUST be overridable with an explicit flag. This
keeps the migration idempotent in the byte sense MIG3 requires, rather than only
in the "same records" sense.

user would want:

| --- | --- |

| 221 achievements | 121 achievements + 100 questions |

The 2 skipped rows have the literal string `None` in every column — a blank

## 16. Deferred: writing support and AI-assisted writing

Two pieces of new functionality, requested for after the equivalent tool is done.
**Neither is designed here**, because the material itself is not yet drafted — but
the constraints that will decide their shape are already knowable, and recording
them now is cheaper than rediscovering them later.

### 16.1 Writing-support material

Additional reference material presented to the user while they write: prompts,
phrases, a house style, an achievements bank, example bullets — the kind of thing
that gets pasted into a story field.

**Not yet specified, because the content is not yet decided.** The open questions
are structural, not cosmetic:

- Is this a new synced entity (so it follows the user between devices), or is it
  static content shipped with the app (a constant, no sync, no storage)? A synced
  entity is more useful and costs a schema version and a merge case.
- Is it free text, or structured? A list of prompt strings is trivial; a
  tagged, searchable, category-linked bank is a feature in its own right.
- Does any of it get injected into the document, or is it read alongside it? If it
  can be injected, D13 (no untrusted text as markup) applies to it as well.
- Is it authored in-app, or imported once from a file?

**These are recorded so the Phase 9 scope conversation starts from them rather than
from nothing.** The entity will need `id`, `updatedAt` and `deletedAt` like
everything else if it syncs (§5.3, §6.4).

**This is where the fit diagnostics from D32 lead.** A fit report that says "this
achievement will run to four lines" is a writing problem surfaced at exactly the
moment it becomes a document problem. Writing-support material — an achievements
bank, example bullets, a length guide — is the answer to what the user does next,
and the fit report is what makes them open it. Designing them together is likely
better than shipping the diagnosis in Phase 2 and the treatment in Phase 9.

### 16.2 AI-assisted writing

Integration with an AI assistant to help write stories and achievements.

**The one constraint that decides this, stated up front:** a static site with no
server cannot hold a shared API key. G1 rules out a proxy, and any key compiled
into the bundle is public the moment the site is deployed. That leaves exactly one
option compatible with the architecture:

> **Bring your own key.** The user supplies their own provider key, it is stored
> only in their browser, it is never synced and never included in an export.

That is workable, but it has consequences that MUST be designed for rather than
discovered:

- **SEC1 has to be amended.** It says the app talks to exactly two third-party
  origins. Any AI integration adds a third. The CSP is the thing that keeps the CV
  from leaking to anywhere else, so widening it is a deliberate, reviewed change.
- **The key sits next to the CV.** The browser will hold both the document and a
  credential that can spend money. D13 (no `dangerouslySetInnerHTML`) and SEC5
  (`check:secrets`) stop being hygiene and become the control that keeps it there.
  The blast radius of an XSS or a malicious dependency goes from "reads your CV" to
  "spends your money".
- **The trust boundary widens.** SEC2 currently says the Dropbox App Folder is the
  boundary. Sending CV text to an AI provider is a second disclosure of the same
  data to a different company, and the user should be told when it happens, not
  discover it in a privacy policy.
- **The zero-integration baseline is strong.** The user can already select a
  paragraph, paste it into ChatGPT, and paste the answer back. Any integration has
  to beat that on convenience, not on capability. Worth saying plainly before
  building it, because a thin wrapper around a copy-paste can be a net loss.
- **Provider, model, streaming and cost are all undecided**, and will be decided
  against a provider that may not be ChatGPT when this phase starts. The spec
  should name a provider abstraction, not a vendor, for the same reason sync does.

### 16.3 When

Both sit **after** the first production release and after the SQLite migration
(Phase 8), so the tool is complete and holding the user's data before it grows new
kinds of data. Phases 9 and 10 in §13 carry them.
